# Общие правила контента BDS

Один источник для всех конвейеров: wiki (`bds-wiki`), блог (`bds-article`), спутники (`bds-satellites`),
новости (`stack-radar`). Решение: [ADR 0001](../docs/adr/0001-content-pipelines-unification.md), п. 1, 12, 13.

Проект держит копию нужных правил с шапкой `Форк: techfriends-eng/bds-content@<sha>, rules/content-rules.md`.
Сторож `tools/fork_drift.py` краснеет, если этот файл изменился после форка.

Правила действуют только на новые и изменённые статьи. Опубликованные статьи не правим и пакетно не линтуем
(решение автора 2026-11-15).

У каждого правила есть код. Линтер пишет код в строке провала, чтобы по нему находился этот файл.

| Код | Правило | wiki | blog | sat | news |
|---|---|---|---|---|---|
| R1 | Нет «:» в заголовке, SEO Title и Description | да | да | да | да |
| R2 | Главные термины в лиде выделены `<strong>` | да | да | да | да |
| R3 | Выбор главных терминов | да | да | да | да |
| R4 | `&nbsp;` перед лидом | да | — | — | да |
| R5 | Mermaid не вертикальный | да | да | да | — |

## R1. Нет «:» в заголовке, SEO Title и Description

В этих полях двоеточий нет:

- заголовок записи (H1, «Заголовок Gutenberg», `# ...` новости);
- заголовки разделов H2 и H3;
- SEO Title (поле Yoast);
- Description (мета-описание Yoast).

Вместо двоеточия пиши два предложения, тире нельзя (Style Guide), скобки можно только в SEO Title.

- Правильно: «Bloom-фильтры Parquet в Iceberg для пропуска строк».
- Неправильно: «Iceberg: Bloom-фильтры Parquet для пропуска строк».

Исключение одно: двоеточие внутри идентификатора без пробела после него, например `qwen2.5vl:7b`.

Проверка: в поле нет `:` с пробелом или концом строки после него. Провал, а не предупреждение.

Лимит двоеточий в теле статьи остаётся профильным (wiki 3, blog 5, news 3, sat 0) и в R1 не входит.

## R2. Главные термины в лиде выделены `<strong>`

Первое упоминание каждого главного термина (R3) в лид-абзаце стоит в `<strong>`. Курсив `<em>` для
терминов не используется (решение автора 2026-11-15, отменяет `<em>` из bds-wiki 6.7.0).

- Каждый термин выделен один раз, при первом упоминании. Дальше по тексту не выделяется.
- В лиде нет других `<strong>`, кроме главных терминов.
- В новостях, где текст пишется в Markdown, это `**термин**`, при сборке HTML он становится `<strong>`.

Профиль wiki строже. Лид открывается `<strong>` с заголовком Gutenberg посимвольно, и это единственный
`<strong>` лида. Совпадение нужно плагину Encyclopedia.

- Правильно: `<p><strong>Data contract</strong> (контракт данных) это машиночитаемое соглашение ...`
- Неправильно: `<p><em>Data contract</em> (контракт данных) это ...`

Новость, пример.

> **Dremio** рассказал, как **Bloom-фильтры** **Parquet** помогают **Iceberg** пропускать строки ...

Проверка: каждый термин из списка R3 встречается в лиде внутри `<strong>`, и других `<strong>` в лиде нет.

## R3. Выбор главных терминов

Главные термины берутся из заголовка записи. Их 2–4.

1. Продукты и технологии из заголовка: Iceberg, Parquet, Kafka, ClickHouse.
2. Ключевое понятие из заголовка: Bloom-фильтр, партиционирование, CDC.
3. Вендор или автор источника, даже если его нет в заголовке: Dremio, Confluent, Databricks.
   В новостях это поле `company` источника.

Не термины: глаголы, оценки, версии отдельно от продукта, общие слова («данные», «система», «строки»).
Термин пишется в той форме, в какой стоит в лиде: «Bloom-фильтры», а не «Bloom-фильтр».

В wiki главный термин один, он равен строке «Термин» meta. Вендор в wiki не выделяется.

Список терминов пишется в meta строкой `Главные термины: A, B, C`. Её читают линтер (R2) и публикация (R6).

## R4. `&nbsp;` перед лидом

Первая строка статьи `&nbsp;`, за ней лид-абзац. Пустая строка визуально отделяет текст от оглавления.

- wiki: уже так, правило не меняется.
- news: лид идёт сразу за H1, поэтому `&nbsp;` ставится между H1 и лидом при сборке, а не моделью.

Проверка: первый блок тела `&nbsp;`, второй `<p>`.

## R5. Mermaid не вертикальный

Схема читается слева направо, чтобы картинка не вытягивалась в длинный столбец.

- `graph` и `flowchart` только с направлением `LR` или `RL`. `TB`, `TD`, `BT` дают провал.
- `subgraph` внутри схемы тоже `direction LR`, если в нём больше двух узлов цепочкой.
- Длинная цепочка из 6+ узлов делится на две схемы или на `subgraph` в ряд.
- `sequenceDiagram`, `stateDiagram-v2`, `erDiagram` разрешены. Для `stateDiagram-v2` ставь `direction LR`.

Проверка в два слоя:

1. линтер по коду в meta: направление `graph`/`flowchart`;
2. рендер по PNG: ширина не меньше высоты. Выше, чем шире, значит провал, схему переделывают.

## R6. Метки и рубрики WP (news)

- **Метки (tags)** ставятся из главных терминов R3 через `toolkit` `ensureTags`.
  - Сначала ищется существующая метка по смыслу, а не только по точному совпадению: slug, имя,
    регистр, число, русская и английская форма («Bloom-фильтры» = `bloom-filter` = «Bloom filter»).
  - Нет существующей, а термин по смыслу есть в заголовке, — создаётся новая. Новых меток на одну
    новость может быть несколько (решение автора 2026-11-15). Вендор из R3 тоже получает метку.
  - Новая метка: имя в форме термина в единственном числе («Bloom-фильтр», «Iceberg»), slug латиницей
    в нижнем регистре через дефис (`bloom-filter`, `iceberg`, `dremio`).
  - Слова не из списка R3 меток не получают.
- **Рубрики (categories)** не трогаем. URL новости строится из главной рубрики, её смена меняет адрес.
  Сейчас рубрики фиксированы: 38, 114.

Метка даёт перелинковку: страница `/blog/tags/<метка>/` собирает все материалы по продукту.
