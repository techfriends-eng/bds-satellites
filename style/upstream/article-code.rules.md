# Стадия 2. Код и прогон на progon для статьи блога

Вторая из четырёх стадий (см. K0 ядра). Начинается с брифа, заканчивается реальным выводом
прогона в брифе и кодом в репозитории. Текст статьи на этой стадии не пишется. Пока вывода нет,
писать нечего.

Порядок жёсткий, как в v3.4: код, публичный RUNBOOK, прогон, пуш. Ссылка на код существует до
текста статьи, и после публикации к статье возвращаться не надо.

## Порядок действий

### 1. Прочитать бриф и карточку

`blog_articles/<slug>_brief.md`. Если файла нет, стадия 1 не отработала: скажи об этом автору и
не начинай с середины. Из брифа берутся slug, версии ПО, список демо, сценарии сравнения и
состав Docker-стенда, согласованные на гейте.

Карточку `stand_progon.md` прочитай, если она ещё не читалась в этой сессии. Главное в ней это
как поднять сервер, бюджет памяти и что на сервере уже есть.

### 2. Где что лежит

- **Исходник кода** пишется на wsa100 в клоне `~/work/articles_code/blog/<slug>/`. Это
  единственная правка кода, на сервере файлы не редактируются.
- **Прогон** идёт на progon в `~/work/blog/<slug>/`. Туда код приезжает через `rsync`, оттуда
  обратно забирается `run_output.txt`.
- **Служебные файлы прогона** (`selfcheck.py`, `recon.py`, `compose.yaml` стенда, если он не
  часть статьи) лежат на wsa100 в `~/work/blog/<slug>/` рядом, вне клона, и в репозиторий не
  попадают.

Первая команда стадии синхронизирует клон:

```
git -C ~/work/articles_code pull --ff-only
```

### 3. Поднять progon

```
ssh -o ConnectTimeout=10 progon true
```

Если сервер не отвечает, он остановлен. Подними его по карточке: `stand_progon.sh up`, когда на
wsa100 есть AWS CLI. Если CLI нет, спроси автора кнопками AskUserQuestion «Включил» / «Не
сейчас» и жди. На «не сейчас» стадия останавливается, бриф остаётся как есть.

Сервер сам выключается после 30 минут простоя. Пока идёт прогон или работают контейнеры, сторож
его не трогает. Длинная пауза между шагами (написание кода больше получаса) означает, что
сервер придётся поднять ещё раз, это нормально.

### 4. Долгое качается первым

Образы Docker, модели, датасеты, тяжёлые пакеты ставятся в фон первой же командой на сервере, до
всего остального:

```
ssh progon 'cd ~/work/blog/<slug> && nohup docker compose pull > pull.log 2>&1 &'
```

Проверяются в конце, когда код уже написан (K9 ядра).

### 5. Разведка одним скриптом и пилотный замер

Незнакомая библиотека требует выяснить одно и то же: что установилось, какие версии, что торчит
в публичном API, сколько занимает один вызов внешнего сервиса. Всё это собирается в один
`recon.py` и даёт один лог. Шаблон лежит в карточке стенда.

**Пилотный замер обязателен и идёт до полного прогона.** Один вызов внешнего API или модели на
минимальном входе показывает масштаб времени и денег. Результат пишется в бриф.

### 6. Демо-файлы

Требования:

- **Первая строка каждого файла это комментарий с пином версии** и честным происхождением:
  `# openai 2.3.0, OpenRouter API, прогнано на стенде 2026-10-20`. Прогон не выдаётся за
  документацию и наоборот.
- **Каждый файл самодостаточен.** Его можно взять из репозитория и запустить, не собирая по
  кускам из статьи. Заглушки вида «остальное как в предыдущем примере» запрещены.
- **Комментарии по ключевым шагам на русском**, по делу, без шума на каждой строке.
- **Имена по K2 ядра**, без слов `blog` и `article`: путь до папки уже говорит, к чему код.
- **Практики больше, чем в Wiki.** Лонгрид показывает два-четыре сценария по плану: базовый
  путь, продвинутый, граничный случай. Для сравнения нужен одинаковый сценарий на двух
  инструментах с замером. Каждый файл закрывает один сценарий.
- **Секреты только из окружения**: `os.environ["OPENROUTER_API_KEY"]`. На сервере ключи лежат в
  `~/work/blog/.env` (кладёт автор), прогон подхватывает их через `set -a; . ~/work/blog/.env`.
  Если нужного ключа нет, скажи автору и не прописывай ключ в код ни на минуту.
- `requirements.txt` с точными версиями по факту `pip freeze` для пакетов статьи.
- **Docker-стенд** описывается в `compose.yaml` статьи, если читатель должен поднять его сам.
  Образы с точным тегом, без `latest`. У каждого сервиса `mem_limit`, сумма не больше 12 ГБ.
  Порты публикуются только на `127.0.0.1`. Имя проекта `blog-<slug>`.

**Черновая проверка до прогона.** Логику можно прогнать на wsa100 с заглушкой внешнего сервиса.
Это ловит опечатки и разошедшийся API раньше стенда. Docker и тяжёлые пакеты на wsa100 не
ставятся, у станции 1 ГБ памяти.

### 7. Публичный RUNBOOK, `selfcheck.py` и прогон

`RUNBOOK.md` в папке кода пишется от лица читателя, который поднимает всё у себя. В заголовке
окружение: версии, что должно быть доступно, какие переменные выставить. Каждый шаг содержит:
- что делаем;
- блок кода;
- что должно быть в выводе;
- как понять, что шаг прошёл.

В конце раздел «если не так».

**Что вырезаем из RUNBOOK:**
- ключи, токены, SSH-конфиги;
- имена progon и wsa100, внутренние адреса, запуск сервера и сторож простоя;
- `rsync` и `--detach`;
- чек-лист скриншотов.

Это кухня процесса, а не технология статьи.

Рядом, вне клона, собирается `selfcheck.py` из шаблона `selfcheck_template.py` в корне
`bds-wiki-articles`. Правятся только списки `VERSIONS` и `DEMOS`. Если статье нужен стенд,
первым демо идёт `docker compose up -d --wait`, последним `docker compose down -v`.

Перенос и запуск:

```
ssh progon 'mkdir -p ~/work/blog/<slug>'
rsync -a --exclude .venv ~/work/articles_code/blog/<slug>/ ~/work/blog/<slug>/ progon:work/blog/<slug>/
ssh progon 'cd ~/work/blog/<slug> && python3 -m venv .venv && .venv/bin/pip install -q -r requirements.txt'
ssh progon 'set -a; . ~/work/blog/.env 2>/dev/null; set +a; python3 ~/work/blog/<slug>/selfcheck.py --detach'
```

Проверка ровно одной командой, она отвечает и «идёт», и «готово», и «упало»:

```
ssh progon 'cat ~/work/blog/<slug>/.status 2>/dev/null || tail -c 400 ~/work/blog/<slug>/run_output.txt'
```

**Ритм проверок.** Первая проверка через полминуты после старта, чтобы поймать падение на
старте. Дальше один длинный сон на ожидаемое по пилоту время и одна проверка. Ждать фоновую
команду через Monitor, а не опросом.

После «готово» вывод забирается на wsa100:

```
rsync -a progon:work/blog/<slug>/run_output.txt ~/work/blog/<slug>/
```

**Если прогон упал**, правишь код на wsa100, переносишь и повторяешь сам. С вопросом на каждый
шаг к автору не ходишь.

**Неудобный результат это тоже результат.** Если замер вышел не в пользу технологии статьи или
модель ошиблась, это фактура для раздела ограничений. Подгонять демо до красивой картинки нельзя.
Такие места пишутся в бриф отдельной строкой.

**Уборка.** После прогона контейнеры проекта `blog-<slug>` остановлены и удалены вместе с
томами. Образы остаются в кэше сервера для следующих статей. Каталог `~/work/blog/<slug>/` на
сервере не удаляется до сдачи статьи.

### 8. Репозиторий

Организация и репозиторий `BigDataSchoolRU/articles_code`, ветка main, каталог `blog/`. Одна
подпапка на статью, имя папки это slug без добавок.

```
articles_code/
└── blog/
    ├── README.md                 <- оглавление со ссылками на статьи
    └── <slug>/
        ├── README.md
        ├── requirements.txt
        ├── compose.yaml          <- если читателю нужен стенд
        ├── <файлы кода>
        └── RUNBOOK.md
```

`README.md` папки содержит:
- название статьи;
- canonical URL;
- состав файлов, по строке на файл;
- окружение кратко;
- как запустить по шагам.

Плюс строка про статью в оглавлении `blog/README.md`. Если оглавления ещё нет, оно создаётся с
этой строкой.

**Мусор не коммитим:** `.venv`, `__pycache__`, логи, ключи, .env, `run_output.txt`, `.status`.
Служебные файлы прогона в клон не попадают изначально.

**Пуш подтверждается автором** кнопками AskUserQuestion: покажи `git -C ~/work/articles_code
status --short` и дифф по именам файлов. После «да» выполни `git -C ~/work/articles_code add
blog/<slug> blog/README.md`, `commit -m "feat: демо к статье блога <Заголовок>"` и `push origin
main`. Пуш идёт с wsa100 через `gh` по https. Если на гейте было выбрано «без пуша», папка
остаётся готовой к пушу, и это пишется в бриф.

Строка баннера собирается здесь и кладётся в бриф целиком:

```
По традиции весь код используемый в статье выкладываем на наш GitHub репозиторий
[github_banner url="https://github.com/BigDataSchoolRU/articles_code/tree/main/blog/<slug>" text="НАЗВАНИЕ СТАТЬИ"]
```

### 9. Скриншоты

**Скриншоты обязательны в каждой статье и снимаются на этой стадии, сразу после прогона.** Это
требование автора (2026-10-21). Откладывать их на стадию 3 или писать «кандидат на скриншот»
нельзя.

Минимальный набор:
- **ключевой вывод каждого сценария практики**: фрагмент `run_output.txt` с цифрами, на которые
  опирается статья, отрендеренный как терминал;
- **UI технологии, если он есть** (Airflow, Kafka UI, Grafana, консоль ClickHouse и т. п.):
  экран, на котором виден механизм статьи, а не стартовая страница. Например, у ретраев это
  страница задачи с попытками, а не Overview DAG.

Чем снимать. На progon стоит headless Chromium в общем venv `~/work/blog/_shot/.venv`
(playwright, как ставить в карточке стенда). Скрипт снимка `shot.py` служебный: лежит на wsa100
в `~/work/blog/<slug>/` и в репозиторий кода не попадает. Вывод рендерится в `<pre>` на тёмном
фоне через `page.set_content`, UI снимается с `127.0.0.1` прямо на сервере. Viewport 1440×900,
`device_scale_factor=2`, JPEG.

Для UI стенд после `selfcheck.py` поднимается ещё раз (`docker compose up -d --wait`, образы в
кэше), сценарий запускается через сам сервис, чтобы история попала в интерфейс, после снимка
снова `docker compose down -v`.

Каждый снимок открой и посмотри сам, прежде чем записывать: виден ли на нём механизм. Пустой или
неинформативный кадр переснимается.

Снимки забираются в `blog_articles/` с именем по K2 (`<slug>_<что_видно>.jpg`). В том же ответе
выдай имя файла, ALT про то, что видно на картинке, и место в статье. Всё это уходит в бриф
сразу, а не в конце работы.

## Чем заканчивается стадия

Допиши в бриф раздел «Стадия 2»:
- папку кода и хэш коммита;
- пилотный замер;
- команду прогона;
- ключевые строки `run_output.txt`, которые пойдут в статью, побуквенно;
- неудобные результаты;
- скриншоты: имя, ALT и место каждого, без них стадия не закрыта;
- грабли.

Отметь чекбокс кода. Роли моделей и версии в таблице «Версии ПО» сверь с тем, что вышло в коде,
и поправь таблицу сейчас: стадия 4 бриф только читает.

Если изменилась реальность стенда (новый системный пакет, образ в кэше, ключ в `.env`), поправь
`stand_progon.md` тем же действием.

Сервер не выключается вручную: его выключит сторож простоя. Если автор просит выключить сразу,
`stand_progon.sh down`.

Дальше вызывается `article-write`.
