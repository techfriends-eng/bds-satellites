# Стадия 1. Новость, разведка и план статьи блога

Первая из четырёх стадий (см. K0 ядра). Заканчивается гейтом с автором и записанным брифом.
Код на этой стадии не пишется, статья тем более. Задача одна: собрать решения, которые дальше
никто не будет пересматривать.

## Порядок действий

### 1. Подготовка

Прочитай карточку стенда `stand_progon.md` по K3 ядра. Если карточка уже прочитана в этой
сессии, повторно её не читаем.

Сверка комплекта одним прогоном:

```bash
python3 tools/check_drift.py bds-article     # в репозитории bds-prompts
```

Расхождение чинится `tools/release.sh bds-article` до начала работы.

### 2. Квота месяца

Считается по K9 ядра до любой другой работы, потому что на седьмой статье остальное не нужно.

```bash
cd <путь к bds-wiki-articles>/blog_articles && python3 - <<'EOF'
import datetime, pathlib, re
month = datetime.date.today().strftime("%Y-%m")
shipped, started = [], []
for brief in sorted(pathlib.Path(".").glob("*_brief.md")):
    slug = brief.name[:-len("_brief.md")]
    meta = pathlib.Path(f"{slug}_meta.md")
    text = meta.read_text(encoding="utf-8") if meta.exists() else ""
    if re.search(r"^- \*\*Статус:\*\* сдано", text, re.M):
        if re.search(rf"^- \*\*Дата сдачи:\*\* {month}", text, re.M):
            shipped.append(slug)
    elif "[x] план" in brief.read_text(encoding="utf-8"):
        started.append(slug)
print(f"{month}: сдано {len(shipped)} {shipped}, в работе {len(started)} {started}, N = {len(shipped) + len(started)}")
EOF
```

Сданные за месяц плюс начатые без сдачи дают N. Каждая статья считается один раз. Если N уже 6, остановись и покажи автору оба
списка. Продолжаешь только по явному «пишем сверх квоты», и тогда это пишется строкой в бриф.
Цифра «статья N из 6 за ГГГГ-ММ» тоже уходит в бриф.

### 3. Исходная новость

На вход приходит одно из трёх. По нему восстанавливается остальное.

- **Ссылка на пост в Telegram-канале отбора.** В посте есть заголовок и ссылка на первоисточник.
- **Наш URL в `/blog/news/`.** Это опубликованный короткий разбор. Из него берутся заголовок,
  первоисточник в референсах и canonical для внутренней ссылки.
- **id записи в stack-radar.** Если у сессии есть доступ к базе радара, поля читаются одним
  запросом. Если доступа нет, попроси у автора ссылку на пост и не ищи обходных путей.

```sql
select id, title, url, source_id, pick_status, site_slug, wp_url
from articles where id = <id>;
```

Новость с `pick_status`, отличным от `approved`, в работу не берётся без явного слова автора:
конвейер рассчитан на новости, прошедшие отбор.

**Habr как источник.** Если новость пришла из `habr-*`, найди первоисточник, на который ссылается
Habr, и работай от него. Habr идёт в референсы как одна из ссылок, а не как основа статьи.

**Главный вопрос стадии.** Ответь одним-двумя предложениями: какой вопрос закрывает статья,
который новость не закрыла. Если ответа нет, а тема исчерпывается самой новостью, скажи автору
прямо. Лонгрид из пересказа это ровно то, чего эта ветка избегает.

### 4. Тема, ключ и slug

- Выведи главный ключ темы, английский оригинал по K2a ядра.
- Из ключа получи файловый slug и URL-slug по K2.
- Собери canonical URL по K5.
- SEO Title подбирается здесь же, до 60 символов, с главным ключом. Шаблон «Что такое X» для
  блога не годится. Блог отвечает на вопросы «как», «зачем», «что выбрать», и формулировка берётся
  по частотности. Wordstat и Google Trends используются, если отдались. Недоступное фиксируется
  строкой «не проверено». Потолок здесь два обращения к вебу, отдельно от разведки.

### 5. Дубль

```
rag_search(query="<ключ ru> <ключ en>", sources=["bds-articles"], k=10, max_per_document=1)
rag_search(query=<тот же>,             sources=["bds-files"],    k=5,  max_per_document=1)
ls blog_articles/ | grep <slug>
```

Наличие материала оценивается по `lexical_coverage` и `coverage_hint`, а не по `score`.

**Короткий новостной разбор по той же новости это не дубль.** Это повод и цель внутренней ссылки.
Дубль это уже существующий практический лонгрид по той же теме и с той же практикой. В таком
случае скажи автору и жди решения: другой угол, обновление старой статьи или отказ.

### 6. Исследование

Разведка идёт субагентом `bds-article:research`. Задание короткое, остальное зашито в агенте:

```
Собери фактуру для статьи блога.
Новость: <заголовок>, <URL нашей публикации или поста>
Первоисточник: <URL>
Тема статьи: <главный вопрос из пункта 3>
Кандидаты в альтернативы для сравнения: <2-4 названия, если уже понятны, иначе «определи сам»>
Выходной файл: <абсолютный путь>/blog_articles/<slug>_research.md
```

Агент вернёт короткую сводку в чат, а полный разбор положит в файл. **Файл читай выборочно**:
нужны версии, механизм, цифры для сравнения и ссылки.

Пункт агента «что выяснить не удалось» переносится в бриф строкой «не проверено». Тихо добирать
недостающее лишними запросами нельзя. Если без факта план не складывается, допускается одно-два
обращения своими руками, и их число пишется в метрики разведки.

**Если агент недоступен**, разведка идёт своими руками с тем же потолком в шесть обращений, а в
бриф пишется строка о том, что субагент не использовался.

### 7. Теория и сравнение

Это две вещи, ради которых статья блога длиннее Wiki. Обе решаются здесь, а не на стадии 3.

- **Теоретический блок.** Выбери два-три механизма, без которых практика непонятна: как устроено
  под капотом, почему так, какие компромиссы. Для каждого укажи источник из разведки. Теория
  обслуживает практику, а энциклопедический обзор всего подряд в неё не входит.
- **Сравнение.** Выбери 2-4 альтернативы, которые читатель реально рассматривает вместо
  технологии статьи, и 4-7 критериев таблицы: модель развёртывания, лицензия, производительность,
  зрелость, стоимость, порог входа. Под каждую ячейку должна быть опора: документация, бенчмарк с
  условиями или собственный замер стадии 2. Ячейка без опоры помечается «не проверено» и в
  таблицу статьи не идёт.
- **Замер в практике.** Если сравнение можно подкрепить прогоном на progon (одинаковая задача на
  двух инструментах, время, объём, число вызовов), запланируй это в списке демо. Собственная
  цифра со стенда дороже любой чужой таблицы.

### 8. Стенд под практику

Проверь по карточке `stand_progon.md`, помещается ли практика на сервер: Python, pip, Docker,
сетевые вызовы наружу, бюджет памяти контейнеров 12 ГБ.

- Помещается: режим LIVE progon, в брифе строка с оценкой памяти и времени прогона.
- Docker-стенд не влезает в бюджет (несколько тяжёлых сервисов сразу): вынеси на гейт урезанный
  состав стенда или разнесение сценариев по очереди. Урезать практику молча нельзя.
- Нужен API-ключ внешнего сервиса: проверь по карточке, лежит ли он в `~/work/blog/.env` на
  сервере. Если ключа нет, это вопрос гейта: кладёт его автор, ассистент ключи не переносит.

### 9. Перелинковка

Кандидаты ищутся в RAG-индексе:

```
rag_search(query="<ключ ru> <ключ en> <смежные>", sources=["bds-articles"], k=10, max_per_document=1)
rag_search(query=<тот же>, sources=["bds-courses"], k=5,  max_per_document=1)
```

URL берутся из выдачи и копируются побуквенно. **Собирать URL по формуле из slug'а запрещено.**

Обязательный минимум в статье:

- **Наш пост-новость** в `/blog/news/`, если исходная новость опубликована. Ссылка ставится в
  разделе контекста.
- **Одна статья блога** по смежной теме, кроме нашего поста-новости.
- **Одна текстовая ссылка на страницу курса.**
- **Минимум одна внешняя ссылка в теле статьи**, обычно на первоисточник или документацию.
- **Для цикла** ещё ссылка на другую статью цикла по `<series>_series.md`. Canonical годится
  сразу, даже если статья не опубликована.

Выбор фиксируется в брифе одной строкой обоснования. Ссылок на `/wiki/` не ставим: термины
словаря подсвечивает плагин Encyclopedia (K8 ядра).

### 11. Структура статьи

Используются только H2 и H3, они идут в автоматическое Содержание. Каркас лонгрида обязательный,
названия разделов свои, под тему.

1. **Лид-абзац** без заголовка. Что произошло и почему тема шире новости. Главный ключ стоит в
   первом предложении.
2. **Контекст.** Одним H2 суть новости, ссылка на наш пост и первоисточник. Новость здесь не
   пересказывается, абзаца-двух хватает.
3. **Теория.** Один-два H2 с H3 внутри: механизмы из пункта 7, схема Mermaid. Самый весомый по
   объёму блок вместе с практикой.
4. **Сравнение с альтернативами.** HTML-таблица по критериям из пункта 7 и разбор, где какой
   инструмент выигрывает.
5. **Практика.** H2 с H3 по сценариям. Баннер `github_banner` сразу после заголовка H2. Код
   целиком, реальный вывод и разбор вывода.
6. **Ограничения и подводные камни.** Документированные лимиты и то, что вылезло на прогоне.
7. **Когда применять, а когда не стоит.**
8. **Заключение.** Без рекламных призывов. Для цикла здесь стоит мостик к следующей статье.
9. **Референсные ссылки**, заголовок H2. Это 3-5 источников не старше года, первоисточник новости
   обязательно, официальная документация обязательно.

Ориентир объёма: 1800-2500 слов. Распредели его по разделам в плане, чтобы теория и практика не
съели друг друга.

### 12. Визуализации

Для каждой схемы сразу предложи имя файла по K2 и ALT, который описывает содержимое схемы. В
лонгриде обычно две-три схемы: механизм из теории, поток данных или архитектура практики,
иногда схема выбора между альтернативами. Отдельно планируется превью-картинка, одна на статью.

Сам код Mermaid и промпт превью пишутся на стадии 3. Здесь принимаются только решения.

## Гейт

Покажи автору план обычным сообщением. В нём должны быть:
- исходная новость и главный вопрос;
- квота;
- canonical с рубрикой;
- SEO Title;
- теория;
- сравнение;
- структура;
- демо и стенд;
- перелинковка;
- курсы;
- схемы.

Последним действием вызови AskUserQuestion с вариантами «Утверждено, пишем дальше», «Утверждено,
но без пуша», «Есть правки». Если на гейт вынесен выбор стенда под Docker или рубрики canonical,
задай его тем же вызовом отдельным вопросом.

Правки возвращают к плану, а не к исследованию заново.

## Чем заканчивается стадия

Запиши бриф `blog_articles/<slug>_brief.md` по формату K7 ядра. Заполни шапку и раздел «Стадия
1», отметь чекбокс плана, зафиксируй в строке гейта, что именно утвердил автор. Метрики разведки
пишутся туда же.

Дальше вызывается `article-code`. Сама эта стадия код не пишет и статью не начинает, даже если
кажется, что всё понятно.
