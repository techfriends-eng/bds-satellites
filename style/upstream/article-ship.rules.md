# Стадия 4. Проверка и сдача статьи блога

Четвёртая из четырёх стадий (см. K0 ядра). Начинается с брифа и двух готовых файлов,
заканчивается отчётом соответствия, статусом «сдано» в метаданных и пушем в git.

**Бриф на этой стадии только читается.** Ни строки, ни чекбокса в него не дописывается (K7).
Всё, что стадия узнала, идёт в `<slug>_meta.md`.

Проверка идёт в жёстком порядке: сначала машинная, потом смысловая. Ассистент проверяет текст,
написанный в том же контексте, и видит соответствие там, где стороннему глазу видна дырка.
Скрипту всё равно, что ассистент думает о своём тексте.

## Часть 1. Линтер

```bash
cd "<путь к bds-wiki-articles>" && python3 wiki_lint.py <slug> --profile blog
```

**Зафиксируй число провалов на первом прогоне сразу**, до исправлений. Это `lint_fails_first`,
главная метрика качества промпта. Задним числом оно не подгоняется.

Профиль `blog` закрывает механику:
- каталог `blog_articles/`;
- объём от 1800 слов;
- `&nbsp;` перед заголовками, двоеточия в заголовках и в теле (лимит 5);
- два cbanner и ровно один github_banner;
- ссылки на блог, курс и внешний источник в теле, слэши в URL;
- `<h2>Референсные ссылки</h2>` с 3-5 источниками;
- таблица сравнения в тексте;
- `TODO_IMAGE` и ALT, схемы против метаданных, код Mermaid и палитра;
- блоки кода и пины версий, заглушки;
- длинное тире, эмодзи, markdown, голые URL;
- имена файлов, строки «Статус», «Дата сдачи» и SEO Title до 60 символов в метаданных.

Прямые ссылки на `/wiki/` профиль запрещает, как и профиль wiki. Совпадение лида с заголовком не проверяется.

**Отчёт соответствия не пишется, пока линтер не отработал с нулём провалов.** Провалы правятся
в статье, линтер прогоняется заново. Если скрипт неправ, чинится скрипт, и правка объясняется
автору. Обходить проверку нельзя.

Переносы внутри блоков чинятся одним прогоном `python3 wiki_unwrap.py <slug> --profile blog`.

## Часть 2. Смысловая проверка

Проверка идёт субагентом `bds-article:article-review`. Инструменты у него только на чтение.
Пути передаются абсолютные и всем комплектом сразу:

```
Проверь статью блога <slug>. Файлы статьи:
<корень>/blog_articles/<slug>.html
<корень>/blog_articles/<slug>_meta.md
<корень>/blog_articles/<slug>_brief.md
<корень>/blog_articles/<slug>_research.md   (если разведка велась)
<корень>/blog_articles/<slug>_runbook.md

Коды курсов в статье: <код> = <название>, <код> = <название>.
Режим: LIVE progon.
```

Файлы, которых для этой статьи нет, в список не вписываются.

**Результат субагента не принимается на веру.** Каждое несоответствие проверяется по файлу,
выдуманное отбрасывается с пометкой. Метрики субагента идут в отчёт соответствия строкой:
сколько находок, сколько подтвердилось, сколько ложных, его расход.

**Если агент недоступен**, проверка идёт своими руками по списку ниже, а в отчёт пишется строка
о том, что субагент не использовался.

Список ниже тот же, что зашит в агенте. Правя список, правь оба места.

Один пункт остаётся за родителем, потому что агент не видит сессию: **карточка
`stand_progon.md` прочитана, и если реальность разошлась с ней, файл обновлён.**

Идём по каждому пункту явно, фиксируем «ок», «поправлено» или «неприменимо».

- Статья развивает новость, а не пересказывает её: раздел контекста короткий, главный вопрос из
  брифа закрыт.
- Каркас лонгрида соблюдён: теория, сравнение, практика, ограничения, когда применять.
- Теория объясняет механизм, нужный для практики, и опирается на источники из брифа.
- Таблица сравнения есть, каждая ячейка подкреплена источником или замером, после таблицы есть
  разбор.
- Все фактические утверждения подтверждены документацией или прогоном. Числа совпадают с
  `run_output.txt`, версии с фактом установки, замеры поданы с условиями.
- Пин версии в первой строке кода честный.
- Каждый код, упомянутый в тексте, показан целиком. Вывод рядом с кодом реальный.
- Код и публичный RUNBOOK запушены до написания статьи, URL баннера ведёт на `blog/<slug>`. В
  репозиторий не уехали ключи, `.venv`, служебные файлы прогона и детали стенда progon.
- Неудобные результаты прогона из брифа не потеряны и попали в раздел ограничений.
- Коды курсов релевантны теме.
- Каждый внутренний URL взят из выдачи `rag_search` или из брифа и совпадает побуквенно.
- Прямых ссылок на Wiki-страницы нет, термины написаны в форме словаря.
- Ритм не подгонялся под статистику.
- Термины даны с английским оригиналом, имена собственные введены, двусмысленных отсылок нет.
- Списки по правилу сэндвича, сравнения в HTML-таблицах.
- ALT и имена картинок описывают содержимое.
- Главный ключ в первом предложении, без переоптимизации. Референсы свежие, первоисточник
  новости и официальная документация есть.
- Telegram-анонс в метаданных уложился в 400-600 знаков и ведёт на canonical.
- Имена всех созданных файлов соответствуют K2.

Все несоответствия правятся до показа автору. Отчёт с выводом линтера фактом (проверок,
провалов, предупреждений, `lint_fails_first`) дописывается в раздел «Отчёт соответствия»
`<slug>_meta.md`. Статистика переносится из вывода линтера, вручную не пересчитывается.

Хвостов типа «сгенерировать превью» не перечисляем, это типовая работа автора.

## Часть 3. Сдача

1. **Файлы на месте по K4:** `<slug>.html`, `<slug>_meta.md`, копия публичного RUNBOOK в
   `<slug>_runbook.md`.

1a. **Чистка превью.** Если в `blog_articles/` уже лежит `<slug>_preview.jpg`, прогони
   `./preview_clean.sh <slug>` в корне `bds-wiki-articles`. Скрипт отправляет файл через
   `ssh auto08` в сервис watermarks-remover и перезаписывает его без EXIF/XMP/C2PA, как
   wiki_visualizer делает с превью Wiki. Код возврата не 0 значит, что чистка не прошла: превью
   в коммит не берётся, автору сообщается причина. Если превью автор положит позже, перед его
   пушем вызывается тот же скрипт.

1b. **Скриншоты рядом со статьёй.** Каждый файл из раздела «Скриншоты» `<slug>_meta.md`
   скопируй с wsa100 из `~/work/blog/<slug>/` в `blog_articles/media/<slug>/` репозитория
   `bds-wiki-articles`, имя файла не меняется. Оттуда их берёт wiki_visualizer на auto08: заливает
   в медиатеку WordPress и подставляет вместо `TODO_IMAGE` при публикации. Превью и схемы конвейер
   делает сам с approve в Telegram, их в `media/` не кладём. Если файла скриншота нет, публикация
   статьи встанет, поэтому отсутствие сообщается автору сразу.
   ```bash
   mkdir -p blog_articles/media/<slug> && cp ~/work/blog/<slug>/<файл>.jpg blog_articles/media/<slug>/
   ```

2. **Статус и дата.** В шапке `<slug>_meta.md` поставь «Статус: сдано» и «Дата сдачи: ГГГГ-ММ-ДД»
   (сегодня). По этим двум строкам считается квота месяца (K9). Отдельно в «Отчёт соответствия»
   допиши строку полей прогона:
   ```
   prompt_version v1.0-Article, model <модель>, effort <усилие>, mode <режим>,
   messages <число реплик автора>, lint_fails_first <N>, words <слов>
   ```
   Это заменяет запись в реестр, которого у блога пока нет (K8).

3. **Цикл.** Если статья входит в цикл, в `blog_articles/<series>_series.md` в её строке поставь
   статус «сдано». Больше ничего в файл цикла не дописывается.

4. **Публикация в git.**
   ```
   git add blog_articles/<slug>* blog_articles/media/<slug> [blog_articles/<series>_series.md]
   git commit -m "feat: <Заголовок> — статья блога"
   git push origin main
   ```
   Всё это делается в репозитории `bds-wiki-articles`. Без пуша статья остаётся только на диске,
   и стадия не считается закрытой.

**Чего не делаем.** `wiki_add_article` и прочие инструменты реестра Wiki не вызываем, параллельных
трекеров не заводим. Черновик в RAG не кладём.

## Что показать автору

Коротко:
- что сдано;
- ответ линтера цифрами, включая `lint_fails_first`;
- квота месяца после этой статьи (N из 6);
- хэш коммита.

Для цикла добавь, какая статья по роадмапу следующая.

## Чем заканчивается стадия

Итог стадии: статус «сдано» с датой, отчёт соответствия в `<slug>_meta.md` и пуш в git. Бриф
остаётся таким, каким его оставила стадия 3.
