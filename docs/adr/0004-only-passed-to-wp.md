# ADR 0004. В WP уходит только статья, прошедшая проверки; тема без прохода снимается

- Статус: принято (2026-11-21), реализация v0.1.52, пункты 5–6 — v0.1.53
- Дата: 2026-11-21
- Меняет: ADR 0001, решение «провал проверок → черновик WP с комментарием»

## Контекст

По ADR 0001 статья с проваленными проверками уходила в WP черновиком с комментарием о провале, а автор
раз в неделю решал по каждой. Блокировал WP только провал стиля (`STYLE_ITEMS` линтера). На деле:

- Из статей kafka после 15.11 проверки прошла одна из четырёх (723). Остальные лежали в WP черновиками,
  700 даже встала в `future` (расписание ставило по старому отчёту), опубликованный 724 ждал правки.
- Частый провал — R2 (жирный в лиде). Модель ставит `<strong>` не на те слова или лишний раз, правка
  чинит одно и ломает другое. R2 не в `STYLE_ITEMS`, поэтому такие статьи шли в WP.
- Тема, исчерпавшая потолок правок (`gates.maxRevisionsTotal`), висела в `gate_failed` навсегда и
  занимала место в `select.perRun`: новые темы не брались.

Автор 21.11: конвейер должен работать без постоянного вмешательства.

## Решение

1. **Жирный в лиде ставит код, не модель.** `article/html.ts` `leadTerms`: в первом абзаце снимаются
   все `<strong>`/`<b>`, каждый термин из строки meta «Главные термины» оборачивается один раз (первое
   вхождение целым словом вне `code`, `a`; длинные термины первыми). Шаг входит в `normalizeArticle`,
   идёт после черновика, перед проверками и перед публикацией. R2 выполняется по построению.
2. **В WP только `ready`.** Публикация и схемы/превью идут только по `ready`. Провал любых проверок
   (линтер, прогон, ссылки, уникальность, смысловая проверка с high) не создаёт пост и не обновляет
   уже созданный; в журнале `stats.gate_held`. Комментарий о провале в теле поста больше не пишется.
3. **Потолок правок исчерпан — тема снята.** После шага `revise`, если статья всё ещё `gate_failed` и
   правок `revise` по теме не меньше `gates.maxRevisionsTotal`, кандидат уходит в `rejected` с
   причиной «проверки не пройдены за N правок, тема снята», а `pick` сразу берёт одну тему из пула
   (`stats.dropped`). Команда с явными id замену не берёт. Вернуть тему автор может `sat rework <id>`:
   rework теперь принимает и `rejected`.

4. **Вышедший пост принят автором** (уточнение автора 21.11). Тема с постом в статусе `publish` уходит
   в конечный `published` (`acceptLive` в начале каждого прогона и после публикации; пост из
   расписания сверяется с WP до обновления). Такая статья не проверяется, не правится, пост не
   обновляется, ошибок о ней нет. Переделка вышедшего поста — только явной командой `sat adopt`.

5. **У автора в WP два исхода темы: пост в расписании (или вышел) либо поста нет** (автор 21.11:
   «должен быть запланирован на дату или rejected»). Такт и `sat sync` снимают все `gate_failed` с
   выбранным потолком (`sweepExhausted`), а не только правленые в этом такте: правка у таких тем уже не
   шла, и они висели. Невышедший пост `rejected`-темы (черновик, расписание, на проверке) уходит в
   корзину WP (`trashRejected`, REST DELETE без force, `stats.wp_trashed`); вышедший — тема
   `published`, пост не трогается; удалённый руками — `wp_status = deleted`.
6. **Ручная доработка не обходит потолок молча.** `sat rework <id>` отказывает теме с выбранным
   потолком (`stats.rework[].refused`); обойти — `sat rework <id> --force`, и этот флаг ставит только
   автор. 21.11 ручной rework дал «MirrorMaker 2 и перенос позиции консьюмера…» правки 5–6 ($0.79)
   на теме, где вывод стенда противоречил заголовку и текстом её было не спасти.

## Последствия

- WP содержит только прошедшие статьи, расписание `future` не получает брак.
- Уже лежащие в WP черновики с провалом остаются до прохода темы или её снятия (тогда — в корзину WP).
- Вышедшие с провалом (kafka 724) становятся `published` и выпадают из `sat_stuck` после `sat sync`.
- Тема с `run_failed` (стенд не прошёл) не снимается этим правилом: это сбой окружения, не текста.
- Расход растёт на замены: снятая тема стоит до `maxRevisionsTotal` правок, потом пул платит за новую.
