# ADR 0001. Спутники: общий конвейер на TS с тегами, тонкие репо сайтов, контент по форку bds-article

- Статус: принято
- Дата: 2026-10-31 (принято автором 2026-10-31)

## Контекст

Задача: kafka-school.ru, spark-school.ru, python-school.ru получают 1–2 статьи в неделю из второстепенных
источников. Статья включает свой материал, практику с кодом, прогнанным на стенде, и задания. Участие
автора минимальное, Telegram не используется. Требование автора: код и сервисы каждого сайта изолированы
друг от друга.

Прототип (`sat-template`, `sat-kafka`, 2026-10-28…31, Python) проверил цепочку целиком: сбор → дедуп
(URL, simhash, ссылки постов bigdataschool.ru, Stack Radar) → отбор (Haiku) → план и текст (Sonnet) →
прогон кода на progon → проверки → переписывание по реальному выводу → черновик в WP → журнал в BDS Хаб.
Два черновика kafka прошли проверки и лежат в WP как draft (#9183, #9184). Цифры и журнал работ — в
`docs/handoff-wsa100.md` приватного репо `bds-sat-kafka`, грабли — в handbook `gotchas/`.

Прототип не соответствует принятым требованиям:
- `handbook/scripts/audit.sh` даёт 35 % при пороге 90 %. Нет RUNBOOK §1–§12, AGENTS, CHANGELOG/VERSION/тегов,
  gitleaks, CI, selfcheck, `env.example`. Коммиты не в формате Conventional Commits.
- ADR 0002 handbook: логика пишется на TS, а прототип написан на Python.
- Принцип 3 handbook: свои ingest/LLM/WP вместо `toolkit`. Схема «копии шаблона на каждый сайт +
  cherry-pick» тоже противоречит этому принципу: при каждом новом сайте всё собирается заново.
- Стандарт 07: код попадает на хост через tar, а не через git ff-only; путь не `/opt/<app>`; нет `OnFailure`.
  Стандарт 08: нет доменного сторожа «тишина — сбой».
- Оформление статей не по Style Guide блога: двоеточия в заголовках, 4 вида выделения, нет превью и
  схем. Требование «не трогаем bds-article» понято неверно: оно значит «не ломаем работающее», а форк
  разрешён.

## Решение

1. **Репозитории** (стандарт 01, префикс `bds-` у бизнес-специфичных):
   - `bds-satellites` — общий конвейер. TS, Node 22, раскладка `handbook/templates/project`. Домены в
     `src/lib/`: `sources`, `dedup`, `select`, `research`, `generate`, `stand`, `gates`, `visuals`,
     `publish`, `journal`. Точки входа — `scripts/*.mjs`. Релизы тегами `vX.Y.Z`. Из `toolkit` берутся
     `ingest` (лента, канонический URL), `filter`, `llm` (`createChat`), `wp`, `db` (миграции),
     `config` (`readSecret`). Своего аналога этих модулей нет. Если общее понадобится второму
     бизнесу, оно уезжает в `toolkit`.
   - `bds-sat-kafka`, `bds-sat-spark`, `bds-sat-python` — тонкие репо сайтов. В них `config/site.yaml`
     (ленты, темы, курсы, CTA, расписание, лимиты), `prompts/site/` (дополнения к общим промптам),
     `deploy/` (юниты, `env.example`), `ops/` (selfcheck, deploy), RUNBOOK, CHANGELOG. В `package.json` —
     `"bds-satellites": "github:techfriends-eng/bds-satellites#vX.Y.Z"`.
   - Изоляция достигается пином версии: правка общего кода доходит до сайта, только когда сайт сам
     поднимет тег, и делается это отдельным коммитом с прогоном гейта (ADR 0003 handbook). Новый
     сайт — это новый тонкий репо и конфиг, а не новая сборка.
   - `sat-template` переименовывается в `bds-satellites`, `sat-kafka|spark|python` — в `bds-sat-*`
     (`gh repo rename`, история и редиректы сохраняются). Код прототипа остаётся в истории как
     эталон поведения.

2. **Контент — форк правил bds-article**, исходники не меняются:
   - Правила текста — форк `bds-prompts/system-prompts/plugins/bds-article/skills/{article-plan,
     article-write,article-ship}/rules.md` (Style Guide V10-Blog) в `bds-satellites/style/`. В шапке
     указан исходный коммит. Отличия для спутников записаны отдельным файлом `style/sat-delta.md`:
     CTA вместо `[cbanner]`, если на сайте нет шорткода; без Telegram-анонса; объём; задания.
   - Машинная проверка — форк `bds-wiki-articles/wiki_lint.py` с профилем `sat`. Python здесь
     допустим: это линтер контента (ADR 0002 handbook). У линтера есть эталонные входы и выходы
     (стандарт 06). Проверки: двоеточия (в заголовках 0, в тексте ≤ 5), не больше двух видов
     выделения, термины только `<strong>`, без длинного тире, без голых URL, код в
     `<pre class="EnlighterJSRAW">`, вывод `generic`, `<img>` схем совпадает с метаданными.
   - Модель пишет сразу WP-HTML по Style Guide, а не markdown. Смысловая проверка и переписывание по
     реальному выводу из прототипа сохраняются.
   - Визуальные элементы:
     - Схемы Mermaid в фирменной палитре (B5.1) рендерятся на progon через mermaid-cli в Docker
       (ADR 0004 handbook) и загружаются через `toolkit/wp` `uploadMedia`.
     - Превью (B5.2) генерирует модель картинок через OpenRouter, затем на progon чистятся метаданные
       (EXIF/XMP/C2PA, `exiftool`), как это делает watermarks-remover. Новый сетевой путь
       progon → auto08 не нужен.

3. **Эксплуатация на progon** (стандарты 05, 07, 08):
   - На каждый сайт: пользователь `bds-sat-<site>`, код `/opt/bds-sat-<site>` (клон по read-only deploy
     key), секреты `/etc/bds-sat-<site>.env` (`640 root:bds-sat-<site>`), состояние
     `/var/lib/bds-sat-<site>`, compose-проекты `sat-<site>-<id>`, лимит стенда 6 ГБ.
   - `deploy/bds-sat-<site>.service` + `.timer`: свой день, 02:00 МСК, `Persistent=true`,
     `OnFailure=alert@%n.service`. Прогон пропускается не в свой день, при `PAUSE` и при нехватке
     памяти. Lock `/run/bds-sat-<site>/run.lock` сторож простоя считает занятостью.
   - Деплой — `ops/deploy.sh` на progon: чистое дерево → `git fetch && git merge --ff-only` → `npm install`
     → selfcheck → smoke `--dry-run`. С wsa100 он вызывается по ssh. Это отклонение от `ops_run`
     (стандарт 07): на progon нет MCP-шлюза, сервер включается по требованию. Отклонение оформляется
     ADR в репо сайта.
   - Журнал — база `sat` на auto08 (уже есть, см. RUNBOOK stack-radar §5). Хаб читает её через FDW на
     supan8n. Схема переходит в миграции `bds-satellites` (`toolkit/db`).
   - Мониторинг: `toolkit/ops/monitoring` на progon (тревоги в тему LOGS). На auto08 доменный сторож
     в `checks.d/bds-satellites.sh` поднимает тревогу, если по сайту нет успешного прогона в
     `sat.runs` 8 дней или нового поста в WP-сайта 10 дней.

4. **Процесс:** ветки `feat/*`, Conventional Commits, гейт
   `test:unit && typecheck && lint && shellcheck && gitleaks`, CI, тег на релиз. До первого деплоя —
   `audit.sh` ≥ 90 % по `bds-satellites` и `bds-sat-kafka`.

## Почему

- Оставить Python — отброшено: противоречит ADR 0002 handbook, и общие модули `toolkit` на TS
  остались бы недоступны.
- Копия кода на каждый сайт — отброшено: принцип 3, каждый новый сайт собирается «как в первый раз».
- Один монорепо со всеми сайтами без пинов — отброшено: правка одного сайта перевыкатывает все,
  требование изоляции не выполняется.
- Профиль `sat` прямо в `bds-wiki-articles/wiki_lint.py` — отброшено: правка рабочего конвейера блога.
  Форк его не ломает.
- Чистка превью через watermarks-remover на auto08 — отброшено: нужен новый сетевой путь
  progon → auto08:8765, а `exiftool` локально делает то же.

## Последствия

- Конвейер переписывается на TS по доменам, у каждого домена тесты. Эталон поведения — прототип и
  его журнал: те же входы должны давать те же решения на отборе, дедупе и проверках.
- Таймер `sat-kafka` на progon выключен 2026-10-31 до перехода. Пользователь `sat-kafka`, `/home/sat-kafka`
  и правка сторожа простоя убираются при переходе на `/opt/bds-sat-kafka`.
- Грабли прототипа записываются в `handbook/gotchas/` тем же изменением, что и этот ADR:
  - Claude 5 через OpenRouter: `reasoning.effort`;
  - JSON-ответ с кодом внутри;
  - Application Passwords, Wordfence и логин профиля.
- Готово, если:
  1. audit ≥ 90 %;
  2. линтер `sat` и смысловая проверка проходят на 6–8 черновиках kafka;
  3. в черновиках есть превью и схемы;
  4. автор оценил черновики вручную;
  5. spark и python подключены только новым конфигом и тонким репо, без правок `bds-satellites`.
- Решения автора при принятии:
  - имена репо `bds-satellites` и `bds-sat-*`, старые `sat-*` переименовываются с сохранением истории;
  - баннер курса — ссылкой CTA, шорткод не используется;
  - превью генерирует Gemini Image через OpenRouter.
